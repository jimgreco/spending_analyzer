# Spending Analyzer: runtime database access preparation

Prepared against remote main `cb03f428a9bcae070e64902d4324782953fbe6c3`. These changes are local preparation. No production grants, credentials, schema adoption, data migration, push or deployment was performed by this task.

## Code and compatibility

Normal startup validates `app_schema_versions` plus the reviewed schema manifest. Checks read catalog metadata for columns (type, nullability and default), constraints/validation, indexes, table durability/RLS flags, sequence definitions, app functions/triggers and extensions. Additional objects are allowed; missing or changed required structure is rejected before serving. Contract version 1 is additive; a future breaking migration must explicitly retire incompatible versions and define its rollback floor. Do not regenerate the manifest to hide drift.

`python webapp/migrate.py --adopt-existing` validates an existing schema and records only the compatibility row in one transaction protected by an advisory lock. It does not run the old initializer or historical repairs. If validation fails, stop and review the differences; do not use fresh initialization as a repair workaround. The same migration command without `--adopt-existing` initializes an empty public schema, or validates an already adopted schema as a no-op. All DDL and the compatibility marker commit together, and failures exit nonzero without starting the app. A schema already containing unadopted tables is refused without the explicit adoption flag.

`MIGRATION_DATABASE_URL` is mandatory for the one-shot command and has no fallback to runtime `DATABASE_URL`. The secure owner supplies a migration connection that explicitly assumes `spending_owner` (for example a connection `options` setting of `-c role=spending_owner`). For subsequent migrations, verify `session_user` is the migration login and `current_user` is the owner before execution. Initial adoption may use the existing administrative connection under separate approval before the object-owner transfer; it writes only the compatibility metadata. PostgreSQL defaults follow the actual creator, not membership alone. Never put this connection into the long-lived app, its image, logs or GitHub output. Runtime continues to use only `DATABASE_URL` and refuses startup if `MIGRATION_DATABASE_URL` is present.

## Proposed privileges and exact object scope

The reviewable machine-readable allowlist is [database-access-manifest.json](database-access-manifest.json). The corresponding [SQL proposal](database-access-proposal.sql) enumerates ownership and grants; it is not applied. Production catalog comparison, inverse ACL capture and approval are mandatory before applying it. Names are proposals, not existing or provisioned credentials.

- Nonlogin `spending_owner` owns only the app's public tables, their sequences and app functions; proposed public schema ownership is also that role.
- `spending_migrator` has no elevated flags and uses explicit `SET ROLE` membership in the owner, preferably `NOINHERIT` / membership `INHERIT FALSE`. Runtime has no such membership.
- `spending_runtime` receives database CONNECT and schema USAGE; the exact table privileges below; sequence USAGE where listed; and SELECT only on compatibility/migration metadata. No grant option, DDL, TRUNCATE, sequence UPDATE, or direct app-function EXECUTE.
- Existing database owner, system objects, `plpgsql` extension owner and shared `admin` backup access remain unchanged. No `REASSIGN OWNED BY admin`.
- Do **not** grant DML on all tables by default: that would expose future migration ledgers. Leave future table/sequence access closed and explicitly grant each reviewed object. Under the actual owner in this database use `ALTER DEFAULT PRIVILEGES FOR ROLE spending_owner REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` (without `IN SCHEMA`; schema-local revocation cannot subtract the global default). Also revoke existing app-function PUBLIC EXECUTE. No extension installation or SECURITY DEFINER function is required.

Runtime data tables (11): `cards`, `categories`, `categorization_settings`, `invited_users`, `tags`, `transaction_amount_changes`, `transaction_tags`, `transactions`, `upload_jobs`, `uploaded_files`, `users`.

Runtime metadata tables: `app_schema_versions`. Runtime sequence scope (8) is enumerated in the JSON manifest. Indexes/constraints/triggers follow table ownership; do not grant them separately.

The SQL proposal revokes PUBLIC database privileges only on this selected database and retains explicit migration/runtime CONNECT (shared admin is a superuser). Enumerate and add any other legitimate consumers before approving that statement. This also removes inherited TEMPORARY and CREATE on the selected database. CONNECT grants alone do not isolate other databases when PUBLIC still has CONNECT there. Before final approval, inventory effective PUBLIC, role memberships and schema/table/function grants across the shared instance using metadata only. Either approve scoped CONNECT revocations with every affected consumer explicitly retained, or approve database-specific authentication restrictions. Do not change unrelated tenants to obtain a green test. At minimum verify fresh runtime connections cannot SELECT/INSERT/UPDATE/DELETE other apps' objects and cannot create objects in their schemas. Any surviving PUBLIC connection or schema rights must be recorded, not called isolation.

## App-specific backup and restore gate

Approval request: create a fresh mode-0600 custom-format logical dump of **`spending` only**, in an owner-only directory on the existing host; restore it to a new private database named `codex_role_restore_spending_<UTC timestamp>`; allow only the selected app's approved schema adoption/ownership/grant rehearsal on that copy. No production user-data migration, deletion, source restore, external upload/download, or backup pruning. Retain the copy/dump until the owner separately approves disposal.

Before executing: positively compare source name `spending`, target prefix plus unique suffix, target != source, target absence, instance identity, writable destination, available disk (source estimate + dump + restored indexes/WAL margin), and connection headroom. Abort if any guard fails. Use `pg_dump --format=custom --no-owner --no-privileges`; inspect its TOC privately. Restore using `pg_restore --exit-on-error --no-owner --no-privileges --role=<approved isolated owner>`. Reapply only approved grants after restore; dumps deliberately omit ACLs. Never connect a production worker, email/webhook sender, billing client or external provider job to the restored copy.

Verify source/restore schema inventories and per-table counts from the same consistent snapshot (or a brief coordinated write drain), schema adoption, owner identities, runtime permission probes, and inert app read/start checks without provider credentials. Record timestamps, encrypted/private storage location metadata, archive byte count/digest, restored object counts, completion status and elapsed time. Do not emit app rows or secret-bearing URLs. A filesystem/EBS snapshot or an old successful workflow is not current restore proof. Recovery retains the approved storage/encryption-key custody needed for encrypted app values.

## Rollback boundaries

- Before ownership/credential cutover, the additive compatibility table can remain; the current image still runs under existing admin. Do not undo user rows or restore a stale dump.
- After runtime cutover, prefer the new separation-aware image with the prior approved connection if an ACL omission prevents service; this needs the bounded rollback approval because it restores broad access temporarily. Fix the missing grant and retry within the app scope.
- Pre-separation images run DDL on startup and **cannot use a DML-only runtime**. An old-image rollback would also need the old broad connection and could replay legacy data repairs. It is excluded from this approval scope; retain a separation-aware image as the rollback floor. Any exception needs a separate data-maintenance review and explicit approval. A secret/config rollback does not undo object ownership or grants. Restore those only from the recorded inverse manifest with separate approval.
- No schema down migration or restore over production is part of this change. No data-loss recovery is automatic. Preserve all backups, legacy data and unrelated audit changes.

## Validation

All runtime roles in the local rehearsal were passwordless synthetic NOLOGIN roles in a new PostgreSQL 16 cluster, bound only to a mode-0700 UNIX socket. Application connections used an effective restricted role; negative membership/object tests also used `SET SESSION AUTHORIZATION`. No production credentials or user data were used. This proves effective SQL permissions and app behavior, not production authentication wiring or current backup contents.

The task evidence includes runtime startup, CRUD/sequences/functions/jobs as applicable, denied DDL/ledger writes/elevated roles/cross-app reads, fail-closed schema drift and missing versions, no data rewrites during adoption, transactional migration failure and synthetic custom-format dump/restore with ownership and ACL checks. Ordinary required app suites remain applicable; browser/native/production release gates still run before publication.
